# 风格基调

以下风格来自作者 2017 年的两篇文章（《WeChat Mini Program vs. the Web》和《Why Is CSS So Hard to Learn?》），作为本博客所有文章的写作参考。

## 语气与视角

- **第一人称叙述**，用"我"不用"笔者"（后者显得疏离）
- 情绪要粗粝，不要管理得太好——踩坑时的烦躁、折腾了半天的疲惫、突然搞通的惊喜，都不经打磨地说出来。「MD 就这样吧反正下次还要改」「这里折腾了很久」比「此处需注意」更真实
- 在「想」，不只是在「说」——写的时候像脑子正在转，一个疑问推出下一个，有回应有反驳，不要等想清楚了才下笔，过程本身也是内容
- 对自己的判断诚实：不确定的事情说「我不确定」，走过的弯路坦然承认
- **敢站立场**：给出判断之后可以把问题抛回给读者（「你们觉得呢？」「这不是我想要的，会是你的吗？」），结尾不必是功能完成式的收尾

## 叙事结构

- 以一个**真实场景或问题**开场，不要直接上定义或概念
- 按「遇到问题 → 尝试 → 碰壁 → 再尝试 → 顿悟」的故事线推进，而不是清单式列举
- 「踩坑」和「弯路」是内容的一部分，不要略去——它们比答案更有参考价值
- 结论不必是确定的，可以留有余地甚至反问

## 语言特点

- 中英文**自然混用**，范围不限于技术词汇——日常表达里如果英文更顺嘴就直接用英文，不要刻意翻译。技术词如 Controller、loop、chunk、payload 直接写；非技术词如 tricky、workaround、sweet point、engagement、anyway 遇到合适的地方也可以直接用，不用非得找中文对应词
- 用**加粗**标记核心观点或让读者停下来想一想的句子，不用来装饰
- 类比和比喻要接地气，宁可用「就像苹果时钟那样做个假循环」，不用抽象描述
- 口语化但不啰嗦：「放弃。」可以单独成句；「越补越多，越多越乱」比「随着补丁增多，系统变得复杂」更好

## 格式规范

- **不用** ❌✅❓ 等 emoji 作为小标题或状态标记——这会让文章看起来像 checklist 教程
- emoji 最多偶尔出现在正文里用作语气标点，不超过全文 3 处
- 标题要能体现「这段在说什么」，不要用「方案一/方案二」这种无内容的编号
- 代码块前后要有一两句话交代「为什么这么写」或「这里的关键是什么」，不要裸放代码
- `<kbd>` 标签只用于真正的键盘按键或快捷键（如 <kbd>Ctrl</kbd>+<kbd>C</kbd>），不要为了样式而滥用——文章里没有快捷键内容时就不用

## 什么不该做

- 不要在开头用「本文将介绍……」「本文分为以下几个部分……」
- 不要用「综上所述」「总结一下」做结尾，也不要用「功能完成」「至此实现了 XX」式的句子收尾——像写完交差
- 不要把所有失败方案都写成并列的 `## 方案 N`——应该是一个连续的探索过程
- 不要对读者说教，技术判断说出来让读者自己评估
- 不要把情绪管理得太干净——重写后每段都像「想清楚了再写」，就失去了原声的粗粝感

# 执行方式

## 自动调用（写新文章 / 优化已有文章）

写新文章时：按风格基调输出正文内容，不另作说明。

优化已有文章时：
1. 读取目标文件
2. 对照风格基调，识别不符的部分，简要列出问题点（不超过 5 条）
3. 按风格基调重写，保留所有技术内容（代码块、链接、图片），只改叙事结构和语言表达
4. 直接写入原文件
